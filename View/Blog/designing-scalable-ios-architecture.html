Designing Scalable iOS Architecture.

Good architecture is not about having the most folders or the most patterns. It is about making features easier to change, test, understand, and maintain as the application grows.

A small app can survive almost any architecture. A growing app cannot.

As features increase, the cost of change becomes more important than the number of lines of code. A scalable architecture keeps responsibilities clear so one change does not force unrelated parts of the application to move with it.

Good architecture does not make a project look complicated. It makes change less painful.

1. Architecture Is a Set of Decisions

Architecture is often presented as a diagram. In a real application, it is a collection of decisions:

Where does data come from?→Who owns the rule?
Who owns state?→Who handles navigation?→Can it be tested?

There is no universal architecture that is best for every app. The right design depends on team size, feature complexity, product lifetime, testing needs, and how often the code is expected to change.

2. MVC: Simple Until Responsibilities Collide

Model-View-Controller is easy to understand and can work well for smaller screens and simple features.

Model↔Controller↔View

The problem begins when the controller starts owning networking, formatting, business rules, navigation, validation, and UI updates. At that point, the issue is not the MVC label; it is that too many responsibilities have accumulated in one place.

3. MVVM: Separating View State From the UI

MVVM can provide a useful boundary between a screen and the logic needed to drive it.

View→ViewModel→Service / Data

The important question is not whether every view needs a ViewModel. Use one when it gives you a useful boundary. A tiny view can sometimes remain a tiny view.

4. VIPER: Strong Boundaries for Complex Modules

VIPER splits a feature into five familiar responsibilities.

ViewPresenterInteractorEntityRouter
  • View presents UI.
  • Presenter prepares presentation state.
  • Interactor owns business operations.
  • Entity represents data.
  • Router handles navigation.

VIPER can be a good fit for large and long-lived modules with complicated behavior and multiple developers. Its trade-off is obvious too: more protocols, more files, and more ceremony. For a simple screen, that cost may not be worth it.

5. Clean Architecture: Dependency Direction Matters

Clean Architecture is less about a specific folder layout and more about keeping business rules independent from details such as UI and frameworks.

UI→Use Cases→Domain
Infrastructure↔Interfaces

The useful idea is dependency direction: stable business rules should not depend directly on unstable details.

6. Feature-Based Architecture

Large apps often become easier to navigate when code is grouped by feature instead of by technical type.

Features/
  Profile/
    ProfileView.swift
    ProfileViewModel.swift
    ProfileService.swift
  Orders/
    OrdersView.swift
    OrdersViewModel.swift
    OrdersService.swift

A developer working on Profile should be able to find most of the Profile code in one place. This reduces the “which folder contains the controller?” problem as a project grows.

7. Dependency Injection

Hard-coded dependencies make testing and replacement harder.

protocol UserService {
    func fetchUser() async throws -> User
}

final class ProfileViewModel {
    private let service: UserService

    init(service: UserService) {
        self.service = service
    }
}

The goal is simple: the feature should receive the thing it needs instead of secretly constructing the whole world around itself.

8. State Ownership

Many architecture bugs are really state bugs.

Single source of truth→Predictable updates→Less stale UI

Decide who owns loading state, cached data, form state, authentication state, and other shared values. Duplication may look convenient at first, but competing sources of truth are hard to keep synchronized.

9. Networking and Data Boundaries

Views should not need to understand HTTP details. Keep request building, decoding, caching, and transport behavior behind clear interfaces.

View
 ↓
ViewModel / Feature
 ↓
Repository or Service
 ↓
Network / Database

This separation also makes it easier to swap a live API for a mock during tests.

10. Swift Concurrency and Architecture

Concurrency changes where lifetime and isolation decisions matter.

  • Keep UI state on the appropriate actor.
  • Make task ownership explicit.
  • Respect cancellation.
  • Do not create detached or unstructured work without a reason.
  • Keep shared mutable state behind a clear isolation boundary.

11. Navigation Is Also Architecture

Navigation becomes a real architecture problem when an app has deep links, authentication, tabs, nested flows, and programmatic transitions.

Keep navigation decisions close to the feature or flow that owns them. Avoid spreading knowledge of the entire navigation tree across unrelated views.

12. Architecture Should Make Testing Easier

A useful architecture gives tests somewhere clear to attach.

View→ViewModel→Mock Service

Test business behavior without rendering a screen. Test networking separately. Test navigation rules at the flow level. The architecture should reduce the amount of setup needed to verify one behavior.

13. When Architecture Becomes Over-Engineering

More abstraction does not automatically mean better architecture.

  • Five protocols for a screen with one API call.
  • A repository that only forwards one method forever.
  • Multiple layers with no real change in responsibility.
  • Complex dependency containers for a small feature.
The best architecture is not the one with the most layers. It is the one that makes the next change easier.

14. A Practical Production Architecture

A useful structure for a growing feature might look like this:

Feature
├── UI
├── Presentation
├── Domain
│   ├── Models
│   └── UseCases
└── Data
    ├── Repository
    ├── API
    └── Persistence

This is not a rule to copy into every application. It is a starting point. The boundaries should follow actual responsibilities and change patterns.

15. Architecture Checklist

✓ Responsibilities are clear
✓ State has a clear owner
✓ Dependencies can be replaced
✓ Networking is isolated
✓ Business rules are testable
✓ Navigation has an owner
✓ Async work has a lifetime
✓ Shared state has an isolation strategy
✓ Features are easy to locate
✓ Layers exist for a reason
✓ Complexity matches the product
✓ The next change looks manageable
Architecture should earn its complexity.

When a boundary stops helping the team, revisit it.
