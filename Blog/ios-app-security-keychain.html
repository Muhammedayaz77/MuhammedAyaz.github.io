iOS App Security: Keychain, Tokens and Authentication

Simple security practices for storing tokens, using Keychain and handling authentication safely in an iOS app.

8 min readIntermediateSeptember 2026

Security starts with small decisions

App security is not one feature. It is a set of small decisions about where data is stored, how users authenticate and what the app trusts.

Some mistakes are easy to avoid. One of the most common is storing sensitive values in UserDefaults just because it is convenient.

Do not use UserDefaults for secrets

UserDefaults is useful for preferences such as selected settings or onboarding flags. It is not the right place for passwords, refresh tokens or other sensitive credentials.

Use Keychain for sensitive small values such as authentication tokens and credentials that need protected storage.

A small Keychain wrapper

import Security

final class KeychainStore {
    func save(_ value: Data, key: String) throws {
        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrAccount as String: key,
            kSecValueData as String: value
        ]

        SecItemDelete(query as CFDictionary)

        let status = SecItemAdd(query as CFDictionary, nil)
        guard status == errSecSuccess else {
            throw KeychainError.saveFailed(status)
        }
    }
}

The exact wrapper can be made richer, but keeping Keychain access behind one small type is a good start.

Access tokens and refresh tokens

Many apps use a short-lived access token and a longer-lived refresh token. The access token is sent with API requests. When it expires, the refresh token can be used to get a new one, depending on the server design.

Keep this flow in one authentication layer. Screens should not need to know how token refresh works.

Biometric authentication

Face ID and Touch ID can add a useful layer when the app protects private content. LocalAuthentication can be used to ask the system to verify the user.

import LocalAuthentication

let context = LAContext()

context.evaluatePolicy(
    .deviceOwnerAuthentication,
    localizedReason: "Unlock your account"
) { success, error in
    // Update the app state
}

Biometrics should normally unlock something already protected by the app. They should not replace server-side authentication by themselves.

Never ship real secrets in the app

API keys, private signing secrets and server credentials should not be treated as safe just because the repository is private. A client application runs on a user's device, so anything inside it may be inspected.

If a secret must stay secret, keep the operation on a server that your app calls.

Use HTTPS

Production API traffic should use HTTPS. App Transport Security also gives iOS apps a safer default for network communication. Avoid weakening those protections just to make a development endpoint work.

Be careful with logs

Logs are useful while debugging, but tokens, passwords and personal data should never be printed casually. A forgotten debug log can become a security problem later.

Keep authentication state clear

It helps to have one source of truth for whether the user is signed in. That state can drive the UI while the authentication layer owns the details of tokens and refresh.

Security checklist

  • Use Keychain for sensitive credentials.
  • Use HTTPS for production API traffic.
  • Do not hard-code private server secrets in the app.
  • Keep authentication and token refresh in one layer.
  • Use LocalAuthentication when it adds value.
  • Do not print tokens or passwords in logs.
  • Clear credentials during a real sign-out when required by the product.

Final thought

Good iOS security is usually boring. That is a good thing. Put sensitive data in the right place, keep authentication logic together and avoid trusting the client with secrets it cannot safely protect.
