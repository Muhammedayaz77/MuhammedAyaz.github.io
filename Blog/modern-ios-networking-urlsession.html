Modern iOS Networking with URLSession

A simple production approach to REST APIs, Codable, errors, loading states and clean networking code in Swift.

8 min readIntermediateSeptember 2026

Why networking needs a simple structure

Most iOS apps need to talk to a server. The app sends a request, gets JSON back, turns that JSON into Swift models and then updates the screen.

The problem starts when every ViewModel does this work by itself. URLs, headers, decoding and error handling get mixed with UI code. After some time, changing one API becomes harder than it should be.

A good rule: keep networking code away from the screen. The ViewModel should ask for data, not build every HTTP request.

A small networking layer

A practical setup can have three parts: an API client, request definitions and models.

struct User: Codable {
    let id: Int
    let name: String
}

enum APIError: Error {
    case invalidURL
    case server(Int)
    case decoding
    case network(Error)
}

final class APIClient {
    func getUsers() async throws -> [User] {
        let url = URL(string: "https://example.com/users")!
        let (data, response) = try await URLSession.shared.data(from: url)

        guard let http = response as? HTTPURLResponse else {
            throw APIError.network(URLError(.badServerResponse))
        }

        guard (200...299).contains(http.statusCode) else {
            throw APIError.server(http.statusCode)
        }

        do {
            return try JSONDecoder().decode([User].self, from: data)
        } catch {
            throw APIError.decoding
        }
    }
}

Use Codable for JSON

Codable keeps the model code small and readable. When the server names are different, use CodingKeys instead of manually reading every JSON value.

Handle loading, success and failure

A screen normally has at least three useful states: loading, content and error. Treat them as real states instead of using many unrelated Boolean flags.

enum ViewState {
    case idle
    case loading
    case loaded([User])
    case failed(String)
}

This makes the UI easier to reason about. It also prevents odd combinations such as isLoading == true while an error message is already visible.

What about authentication?

For protected APIs, keep token handling in one place. A networking layer can add an Authorization header without every screen knowing how the token is stored.

Do not put secret API keys directly in the iOS app. Anything shipped inside the app can eventually be inspected.

Timeouts, retry and cancellation

Not every failed request should be retried. A timeout or temporary connection problem may be worth retrying. A 400 response usually needs a different action.

Async/await also makes cancellation easier. If a user leaves a screen, a task can be cancelled instead of continuing work that nobody needs.

Keep the ViewModel small

@MainActor
final class UsersViewModel: ObservableObject {
    @Published private(set) var state: ViewState = .idle

    private let api: APIClient

    init(api: APIClient) {
        self.api = api
    }

    func load() async {
        state = .loading
        do {
            state = .loaded(try await api.getUsers())
        } catch {
            state = .failed("Could not load users.")
        }
    }
}

The ViewModel now focuses on screen state. The API client focuses on HTTP work. This separation is simple, but it makes the code much easier to test and maintain.

My practical checklist

  • Use URLSession for HTTP requests.
  • Use Codable for JSON models.
  • Keep API calls outside the UI layer.
  • Map technical errors into useful app errors.
  • Model loading and failure states clearly.
  • Keep authentication and common headers in one place.
  • Support cancellation for work tied to a screen.

Final thought

Networking does not need a huge framework to be good. A small, clear layer around URLSession is often enough. The important part is keeping responsibilities separate and making failures visible instead of hiding them.
