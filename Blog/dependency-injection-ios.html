Dependency Injection in iOS

A practical and easy way to use dependency injection in Swift so ViewModels stay clean, flexible and easy to test.

7 min readIntermediateSeptember 2026

What is dependency injection?

Dependency injection sounds like a big architecture term, but the idea is simple: a class should receive the things it needs instead of creating them itself.

For example, a ViewModel may need an API service. Instead of creating APIClient inside the ViewModel, pass the service into the initializer.

final class UserViewModel {
    private let api: UserAPI

    init(api: UserAPI) {
        self.api = api
    }
}

Why does this help?

It gives us a clear separation between the class and the concrete object it uses. The ViewModel only cares about the work it can ask the API to do.

The biggest benefit: testing becomes much easier because we can pass a fake service.

Use protocols at the boundary

protocol UserAPI {
    func fetchUsers() async throws -> [User]
}

final class LiveUserAPI: UserAPI {
    func fetchUsers() async throws -> [User] {
        // Real network request
        []
    }
}

final class UserViewModel {
    private let api: UserAPI

    init(api: UserAPI) {
        self.api = api
    }
}

The ViewModel does not know whether the service uses URLSession, a local database or a test object.

Testing becomes simple

final class FakeUserAPI: UserAPI {
    var users = [User(id: 1, name: "Test")]

    func fetchUsers() async throws -> [User] {
        users
    }
}

let viewModel = UserViewModel(api: FakeUserAPI())

Now the test does not need a real server. This makes tests faster and more reliable.

Do not overdo dependency injection

DI is useful, but adding a protocol for every small type can make a project harder to understand. I normally use it at important boundaries such as networking, storage, analytics, payments and other services that may change or need mocking.

Constructor injection is my first choice

Passing dependencies through the initializer makes the requirements visible. If an object needs three services, its initializer shows those three services.

Property injection can hide required dependencies, so I use it only when there is a clear reason.

Composition root

At some point, the app has to decide which real implementations to create. Keep that decision near the application entry point or feature assembly code.

let api = LiveUserAPI()
let analytics = LiveAnalytics()

let viewModel = UserViewModel(
    api: api
)

The rest of the feature can work with protocols. This is often called the composition root. You do not need a complex dependency container to follow the idea.

DI with SwiftUI

SwiftUI also works well with constructor injection. Create the ViewModel outside the view and pass it in, or use environment-based dependencies when the same service is shared across a large part of the app.

Common mistakes

  • Creating services directly inside every ViewModel.
  • Using a global singleton for everything.
  • Creating protocols that add no useful abstraction.
  • Using a large dependency container when a few initializers are enough.

Final thought

Good dependency injection is not about adding more files. It is about making dependencies clear. If a class can be tested without starting the whole application, you are already moving in the right direction.
