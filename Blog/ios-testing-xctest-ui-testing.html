Unit Testing and UI Testing in iOS

A practical guide to XCTest, ViewModel tests, async code and UI testing without making the test suite hard to maintain.

9 min readIntermediateSeptember 2026

Why test iOS apps?

Tests give us confidence when code changes. They are especially useful in apps with many features, multiple developers and regular releases.

The goal is not to test every line. The goal is to protect important behavior.

Start with unit tests

A unit test checks a small piece of logic without starting the whole app. ViewModels, formatters, validation rules and service logic are good examples.

func testLoginWithValidCredentialsSucceeds() async throws {
    let service = FakeAuthService(result: .success)
    let viewModel = LoginViewModel(service: service)

    await viewModel.login(
        email: "test@example.com",
        password: "password"
    )

    XCTAssertTrue(viewModel.isLoggedIn)
}

The test reads like a small story: arrange the objects, perform the action and check the result.

Use fakes instead of real servers

A unit test should not depend on a live API. A fake service lets the test control the response.

final class FakeAuthService: AuthService {
    let result: Result

    init(result: Result) {
        self.result = result
    }

    func login(email: String, password: String) async throws {
        try result.get()
    }
}

Test failure cases too

Happy-path tests are useful, but real apps also fail. Test invalid input, server errors, empty results, expired sessions and other important cases.

A useful question: “What should the user see if this operation fails?” That answer usually tells you what to test.

Testing async code

Modern iOS code often uses async/await. XCTest supports async test methods, so you can wait for the operation directly instead of adding complicated expectations everywhere.

Keep UI tests for real user flows

UI tests are slower than unit tests, so I use them for important journeys rather than every small detail.

  • Launch the app.
  • Sign in.
  • Open an important feature.
  • Perform a key action.
  • Check the result.

This kind of test protects the connection between screens and real user actions.

Make UI tests stable

A UI test becomes painful when it depends on timing, animations or fragile text selectors. Give important controls stable accessibility identifiers.

loginButton.accessibilityIdentifier = "loginButton"

Then the UI test can find the control by a stable identifier instead of depending on its visible title.

Do not put everything in UI tests

If a business rule can be tested without launching the app, test it as a unit. A large suite of UI tests takes longer to run and is harder to debug.

Test architecture matters

Good architecture makes testing easier. When a ViewModel receives its service through dependency injection, a test can replace the real service with a fake.

This is one reason I like keeping UI code, business logic and external services separated.

A simple test pyramid

Many        → Unit tests
Some        → Integration / service tests
Few         → End-to-end UI tests

The exact number depends on the project, but the idea is useful: most fast checks should stay close to the code they protect.

What I check before shipping

  • Important ViewModel logic has unit tests.
  • Success and failure paths are covered.
  • Async operations are tested without real network calls.
  • Critical user journeys have UI tests.
  • Important UI controls have stable identifiers.
  • Tests run in CI before release.

Final thought

A good test suite should make development feel safer, not slower. Start with important behavior, keep tests simple and use the right test level for the job.
