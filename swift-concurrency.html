Swift Concurrency in Production: From Threads and GCD to Actors

Concurrency is not just about moving work to the background. It is about deciding who does the work, where it can run, how long it should live, what happens when it is cancelled, and who is allowed to touch shared state.

A production iOS app rarely performs one piece of work at a time. A screen may be fetching data, decoding JSON, loading images, reading cache, handling input, and updating UI while the user keeps moving.

The difficult part is not making these things happen at the same time. The difficult part is making them happen correctly.

The important concurrency question is not “Which thread should run this?” It is “How should this work be scheduled, isolated, cancelled, and coordinated?”

1. The Evolution of Concurrency on Apple Platforms

Swift Concurrency is the result of years of solving the same problems at different abstraction levels.

Threads→OperationQueue→GCD→Callbacks
async / await→Tasks→Structured Concurrency→Actors
MainActor+Sendable+AsyncSequence

Each step reduced a different kind of manual bookkeeping. Modern Swift does more of the reasoning in the language and compiler, but architecture still matters.

2. Threads: The Lowest-Level Mental Model

A thread is an operating-system execution path. Developers can create one directly:

Thread {
    performHeavyWork()
}.start()

Threads are powerful, but application code usually does not need to manage thread creation and coordination directly. Too many manually managed threads can add memory overhead, scheduling complexity, synchronization problems, and difficult ownership rules.

Thread→Execution

3. Grand Central Dispatch

GCD shifted the developer mindset from creating threads to submitting work to queues.

DispatchQueue.global().async {
    let result = performWork()

    DispatchQueue.main.async {
        updateUI(result)
    }
}

Serial vs concurrent queues

A serial queue executes one submitted block at a time. A concurrent queue can make progress on multiple submitted blocks. The important distinction is that queue and thread are not the same thing.

Important GCD primitives

  • DispatchQueue for scheduling.
  • DispatchGroup for coordinating related work.
  • DispatchWorkItem for representing a unit of dispatch work.
  • DispatchSemaphore for limiting access to a resource.
  • DispatchSource for certain event-driven system work.
  • QoS classes to express relative work importance.

sync vs async

async submits work and lets the caller continue. sync waits for the block to finish. That difference becomes critical when synchronization is involved, and incorrect synchronous dispatch can create deadlocks.

4. OperationQueue

OperationQueue provides a higher-level model around units of work. One of its strengths is explicit dependency management.

Download User→Process User→Save User

When work has dependencies, cancellation, or operation-level state, the abstraction can be useful even in modern codebases.

5. Completion Handlers

Legacy asynchronous APIs often used nested completion handlers.

fetchUser { user in
    fetchPosts(for: user) { posts in
        fetchImages(for: posts) { images in
            updateUI(images)
        }
    }
}

Completion handlers are valid, but large workflows can become difficult to read, test, cancel, and reason about. Error propagation and ownership become especially noisy.

6. async / await

Swift lets asynchronous work look much closer to ordinary control flow.

func fetchUser() async throws -> User {
    ...
}

let user = try await fetchUser()
Important: await does not mean “create a background thread.” An asynchronous operation may suspend the current task, allowing the underlying execution resource to be used for other work.
Task→await→suspend→resume

7. Tasks

A Task represents asynchronous work.

Task {
    let user = try await fetchUser()
    print(user)
}

A task has a lifetime, priority, cancellation state, and execution context. That means the production question is not simply “Can I create a task?” but “Who owns this task, and when should its work stop?”

Cancellation

if Task.isCancelled {
    return
}

try Task.checkCancellation()

Swift cancellation is cooperative. Marking a task cancelled does not automatically terminate every operation inside it. Your code and APIs need to cooperate with the cancellation model.

8. Structured Concurrency

Structured concurrency gives asynchronous work a clearer relationship and lifetime.

Parent Task
Child AChild BChild C

When child work belongs to a parent operation, structured relationships make cancellation and error propagation easier to reason about.

Task groups

await withTaskGroup(of: Result.self) { group in
    group.addTask { await fetchProfile() }
    group.addTask { await fetchPosts() }
    group.addTask { await fetchNotifications() }
}

The key is dependency, not fashion. Independent work may run concurrently; dependent work often should remain sequential.

9. Actors and Shared Mutable State

Concurrency becomes harder when several tasks can access the same mutable state.

actor ImageCache {
    private var storage: [URL: Data] = [:]

    func insert(_ data: Data, for url: URL) {
        storage[url] = data
    }

    func image(for url: URL) -> Data? {
        storage[url]
    }
}

An actor protects its isolated state. The larger architectural idea is powerful: instead of forcing every caller to synchronize access to shared state, make ownership and isolation explicit.

Actor reentrancy

Actors are not “one giant transaction.” When an actor-isolated method reaches an await, the actor can make progress on other work. State read before an await may have changed when execution resumes.

10. MainActor and UI Isolation

UI state naturally belongs to the main actor.

@MainActor
final class ProfileViewModel {
    var name = ""

    func updateName(_ name: String) {
        self.name = name
    }
}

@MainActor is not a synonym for “put all work on the main thread.” It is an isolation boundary for state that needs main-actor access. Expensive work should still be designed so that it does not unnecessarily execute in the UI context.

let result = await fetchData()

await MainActor.run {
    updateUI(with: result)
}

11. Sendable, @Sendable, and Swift 6

Modern Swift also asks whether values can safely cross concurrency boundaries.

Sendable expresses that a type is intended to be safe to transfer between concurrency domains. @Sendable applies the same idea to closures.

This becomes especially important with Swift 6 strict concurrency checking, where issues involving actor isolation, non-Sendable reference types, mutable shared state, and concurrency boundaries become more visible at compile time.

The compiler is no longer just checking syntax. It is helping enforce the concurrency design.

12. Continuations and AsyncSequence

Continuations

Continuations let modern async code wrap older callback-based APIs.

func loadUser() async throws -> User {
    try await withCheckedThrowingContinuation { continuation in
        legacyLoadUser { result in
            continuation.resume(with: result)
        }
    }
}

AsyncSequence

Some asynchronous work produces a stream rather than a single value.

for await event in events {
    handle(event)
}

This is a natural model for notifications, live updates, WebSocket-style events, location updates, and other ongoing asynchronous sequences.

13. Locks, Mutexes, Semaphores and Deadlocks

Actors are not the only synchronization tools. Lower-level systems still use locks, mutexes, semaphores, atomics, and related primitives.

Shared State→Lock / Mutex→Critical Section

These tools can be appropriate in low-level or highly controlled components, but they introduce their own failure modes.

Race conditions

A race condition occurs when the final result depends on the timing of concurrent access to shared state.

Deadlocks

A deadlock occurs when work waits in a cycle and none of the participants can progress. Synchronous dispatch onto the wrong serial queue is a classic example.

Semaphores

A semaphore can limit how many operations access a resource at once. That can be useful, but semaphores can also reintroduce blocking and synchronization complexity, so they should be used deliberately.

14. A Production Example: Photo Feed

Imagine a profile screen that needs to load a user, posts, followers, recommendations, and images.

Profile Screen→ViewModel→Services
async / awaitTaskGroupActor CacheMainActor

A sensible design could use a main-actor-isolated ViewModel, asynchronous service APIs, a task group for independent requests, and an actor for shared image-cache state. When the screen is no longer relevant, associated work can be cancelled.

Sequential work

API A → API B → API C

Use this when the next operation genuinely depends on the previous result.

Concurrent work

        ┌→ API A
Task ───┼→ API B
        └→ API C

Use this when the operations are genuinely independent and the added concurrency is worth the complexity and resource cost.

16. The Production Questions That Matter

✓ Who owns this work?
✓ What happens when the user leaves?
✓ Can this work actually run concurrently?
✓ Is there shared mutable state?
✓ Which isolation domain owns the result?
✓ What happens when the task is cancelled?
✓ Can stale work overwrite newer state?
✓ Do I need a thread, queue, task, or actor?

17. Final Takeaway

Swift Concurrency is not simply a replacement for GCD. It is a broader programming model for expressing asynchronous work, its lifetime, its relationships, its cancellation, and the ownership of mutable state.

The real progression is not “old API versus new API.” It is a progression toward making concurrency relationships easier to express and safer to reason about.

The goal is not to make more things run at the same time.
It is to make asynchronous work behave correctly when many things are happening at once.
